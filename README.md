# Flow — 계좌이체 "입금 확정" 서비스 (기획 초안)

> 시장·노점·플리마켓·개인 판매에서 계좌이체로 결제할 때,
> **"보냈어요" / "안 들어왔는데요"** 를 없애는 서비스.

## 확정 원칙
- **보내는 사람:** 아무 은행앱·간편송금으로 이체 (설치·가입 불필요)
- **받는 사람:** 서비스에 등록한 **지정 입금계좌**로만 수령 — 초기엔 판매자 본인 명의 계좌, 서비스는 돈을 보관·정산하지 않음

시장·경쟁·법률 검토는 [docs/market-and-legal.md](docs/market-and-legal.md) 참고.

---

## 1. 문제 정의

| 상황 | 지금 일어나는 일 |
|---|---|
| 손님이 은행앱으로 이체 후 화면을 보여줌 | 상인은 화면이 진짜인지, 금액·계좌가 맞는지 확인할 방법이 없음 |
| 손님이 많을 때 | 상인이 매번 자기 은행앱을 열어 입금 내역을 확인 → 줄이 밀림, 확인 누락 |
| 같은 금액이 여러 건 | 누가 보낸 건지 구분 불가 |
| 악의적 사례 | 조작된 이체확인 캡처, 이체 후 즉시 다른 계좌로 착각/오타, 지연이체(신규계좌 등) 상태를 완료로 보여주기 |
| 손님 입장 | 분명 보냈는데 상인이 "안 왔다"고 하면 증명할 방법이 애매함 |

**핵심 통찰:** 구매자의 화면은 증거가 아니다.
**유일한 진실은 "판매자 계좌에 실제로 돈이 들어왔는가"** 이다.
따라서 이 서비스의 모든 설계는 *판매자 계좌의 입금 사실*을 기준으로 양쪽에 동시에 "확정"을 알려주는 데 집중한다.

---

## 2. 핵심 가치 (우선순위 순)

1. **입금 확정 (Single Source of Truth)** — 판매자 계좌 실입금이 확인된 순간에만 "확정" 표시. 구매자·판매자 화면에 같은 확정 정보가 동시에 뜸.
2. **즉시성** — 손님이 이체 완료하고 몇 초 안에 상인 쪽에서 "딩동, 15,000원 입금 확정".
3. **간편함** — 계좌번호 받아 적기 / 금액 입력 실수 제거 (QR로 계좌·금액·주문코드 자동 입력).
4. **상인 금융 서비스** — 확정 데이터가 쌓이면 자동 장부, 세금 자료, 정산 리포트, 나아가 매출 기반 금융상품까지.

## 3. 사용 흐름 (시장 노점 예시)

```
[상인]                         [Flow 서버]                     [손님]
  │ 금액 15,000 입력               │                              │
  │──── 결제요청 생성 ─────────────▶│ 주문코드 F7K2 발급            │
  │◀─── QR / 4자리 코드 표시 ───────│                              │
  │                                │◀──── QR 스캔 ────────────────│
  │                                │──── 은행앱/토스 딥링크 ──────▶│ (계좌·금액·받는분통장표시 "F7K2" 자동입력)
  │                                │                              │ 이체 실행
  │                                │◀── 판매자 계좌 입금 감지 ─────│
  │                                │   (금액 + 주문코드 매칭)       │
  │◀── 🔔 "15,000원 입금 확정" ─────│──── ✅ "입금 확정" 영수증 ───▶│
```

- 상인 화면: 큰 글씨 + 소리(스피커 모드), 확정 전에는 절대 초록색이 뜨지 않음.
- 손님 화면: 서버가 판매자 계좌 입금을 확인한 **확정 영수증**(시각·금액·상호·확정번호). 캡처가 아니라 링크로 검증 가능 → 위조 의미 없음.
- 확정이 안 되면: 손님 화면에 "아직 입금이 확인되지 않았습니다" + 원인 안내(지연이체, 계좌 오입력 등).

### 입금 매칭 방법
같은 시간에 같은 금액이 여러 건 들어와도 구분해야 한다.
1. **주문코드** — 이체 시 "받는분 통장 표시"에 4~6자리 코드를 자동 입력 (1순위).
2. **금액 + 시간창 + 보낸 사람 이름** — 코드가 빠진 경우 보조 매칭, 애매하면 상인에게 "이 입금이 이 주문 맞나요?" 원탭 확인.
3. **거래별 가상계좌** (Phase 2) — 주문마다 전용 계좌를 발급하면 매칭 오류가 0에 가까움.

## 4. "입금 확인"을 실제로 어떻게 하나 — 기술 옵션 비교

가장 중요한 부분. 확인 방식이 곧 서비스의 신뢰도이자 규제 수준을 결정한다.

| 방식 | 원리 | 신뢰도 | 실시간성 | 규제/허가 | 비고 |
|---|---|---|---|---|---|
| **A. 은행 입금 푸시 알림 읽기** | 상인 안드로이드폰의 은행/카카오뱅크/토스 입금 알림을 앱이 읽어 파싱 | 중 | 매우 빠름 | 낮음 (자금 보관 X) | MVP용. iOS 불가, 은행 알림 형식 변경에 취약 |
| **B. 오픈뱅킹 거래내역 조회** | 상인이 계좌 연결 동의 → 금융결제원 오픈뱅킹 API로 입금내역 조회 | 높음 | 수 초~수십 초 (폴링) | 오픈뱅킹 이용기관 자격 필요 | 정식 서비스의 기본 축 |
| **C. 거래별 가상계좌 (PG/은행 제휴)** | 주문마다 가상계좌 발급, 입금 시 은행이 웹훅 통보 | 매우 높음 | 즉시 | PG 제휴 / 전자금융업 | 돈이 가상계좌를 거쳐 정산 → 상인 입금 지연·수수료 발생 |
| **D. 오픈뱅킹 출금이체 (간편결제형)** | 손님 계좌에서 직접 출금 → 상인 계좌 입금 | 매우 높음 | 즉시 | 전자금융업(선불/전자지급결제대행) 등록 | 토스·카카오페이와 정면 경쟁 |

**추천 로드맵:** A로 시장 검증 → B로 정식화 → 상인이 원하면 C를 선택 옵션으로.
초기에 **돈을 직접 보관·중개하지 않는 구조(A, B)** 를 택하면 규제 부담이 훨씬 작고, "기존 은행앱으로 이체한다"는 사용자 습관도 그대로 유지된다.

> ⚠️ 실제 출시 전 전자금융거래법, 오픈뱅킹 이용기관 요건, 개인정보보호법(거래내역은 민감 정보)에 대해 법률 검토 필요.

## 5. 신뢰를 지키는 원칙

- **확정 전에는 확정처럼 보이게 하지 않는다.** "요청됨 → 이체 대기 → 입금 확정" 상태를 명확히 분리, 색상·문구 구분.
- **확정 영수증은 서버에서만 생성.** 손님 앱 화면은 서버 상태를 비추는 창일 뿐. 영수증 링크/QR로 누구나 진위 검증.
- **지연이체·착오송금 안내.** 신규 계좌 지연이체 등으로 바로 입금되지 않는 경우를 감지해 양쪽에 "입금 예정, 아직 미확정" 표시.
- **환불도 기록.** 상인이 되돌려 보낸 이체도 동일하게 확정 처리 → 분쟁 시 양쪽 기록 일치.
- **최소 권한.** 거래내역은 입금 매칭에 필요한 범위만 조회·보관, 손님에게는 상인 계좌 전체 정보 노출 안 함(마스킹).

## 6. 상인(개인사업자·소상공인)을 위한 금융 서비스

확정된 입금 데이터 = **정확한 매출 데이터**. 이것이 2차 사업의 기반.

| 단계 | 서비스 | 상인이 얻는 것 |
|---|---|---|
| 기본 (무료) | 자동 매출 장부 | 하루/주/월 매출, 시간대별·품목별 통계, 현금·카드·이체 통합 |
| 기본 | 현금영수증 자동 발급 | 계좌이체도 현금영수증 대상 → 손님 번호 입력만으로 발급 (국세청 연동) |
| 기본 | 세무 자료 내보내기 | 부가세·종합소득세 신고용 매출 자료, 세무사 공유 |
| 확장 | 정산 & 지출 관리 | 도매처 결제, 임대료 등 지출 기록 → 순이익 파악 |
| 확장 | 매출 기반 소액 운영자금 | 확정 매출 이력을 신용 데이터로 활용, 제휴 금융사 대출 연결 (대출중개 등록 필요) |
| 확장 | 정책자금·지원사업 안내 | 소상공인 정책자금, 지자체 지원 사업 자격 자동 매칭 |
| 확장 | 손님 단골 관리 | 재방문 손님 인식, 간단한 쿠폰/스탬프 |

**포인트:** 은행·카드사가 신용평가를 잘 못 하는 영세 상인에게 "현금성 매출을 증명할 수 있는 데이터"를 만들어 주는 것 자체가 금융 접근성을 높인다.

---

## 7. 기존 서비스와의 차별점

| 기존 | 한계 | Flow |
|---|---|---|
| 은행앱 이체 + 화면 보여주기 | 위조·착오 확인 불가 | 판매자 계좌 기준 확정 |
| 은행 입금 알림 | 상인 혼자만 봄, 주문과 연결 안 됨, 장부 없음 | 주문 매칭 + 양쪽 동시 확정 + 장부 |
| 간편결제 QR (카카오페이·토스·제로페이 등) | 손님이 특정 앱 가입 필요, 상인 수수료·정산 주기 | 손님은 **아무 은행앱**으로 이체, 상인 계좌로 바로 입금 |
| 카드 단말기 | 수수료, 단말기 비용, 정산 지연 | 이체 기반이라 수수료 낮거나 없음 |

## 8. 수익 모델 (가설)

- 상인 기본 기능 무료 → 사용자 확보
- 프리미엄 구독 (월 몇천 원): 스피커 모드 다중 기기, 직원 계정, 고급 리포트, 세무 연동
- 금융상품 중개 수수료 (대출·보험 등, 제휴 금융사)
- 가상계좌 옵션 사용 시 건당 소액 수수료

---

## 9. MVP 범위 제안

**목표:** 시장 1~2곳, 상인 20~30명에게 "확정 알림이 실제로 유용한가" 검증.

- [ ] 상인 앱 (Android): 금액 입력 → QR/코드 표시 → 입금 알림 감지(방식 A) → 확정 알림(소리+화면)
- [ ] 손님용 웹페이지 (앱 설치 불필요): QR 스캔 → 계좌·금액·코드 안내 + 은행앱 딥링크 → 확정 영수증
- [ ] 서버: 결제요청 생성, 입금 매칭, 확정 영수증 발급/검증
- [ ] 일일 매출 장부 (기본)

**검증 지표:** 확정까지 걸린 시간, 매칭 실패율, 상인이 은행앱을 따로 여는 빈도 감소, 분쟁 건수.

## 10. 열린 질문

- 손님에게 "주문코드 입력"을 얼마나 자연스럽게 시킬 수 있나? (딥링크 지원 은행 범위)
- 상인들이 계좌 거래내역 접근 권한을 줄 만큼 신뢰를 어떻게 얻나? (시장 상인회·지자체 제휴?)
- iOS 상인은 방식 A가 불가 → 초기부터 B(오픈뱅킹) 확보가 필요한가?
- 온라인 개인 판매(중고거래, 인스타 마켓)까지 확장할 것인가? → 이 경우 "입금 확정 후 발송" 흐름이 에스크로 수요와 연결됨.
